##### 【三角ロジック】

| 要素 | 内容 |
|------|------|
| **データ** | 遠くから「絵を描け」と伝えたいとき、文字列をそのまま実行すると危険である。許可した命令だけを、入れ子のリストで表す方法がある。 |
| **ワラント** | プログラムをデータと同じ形で扱いたいなら、この思考実験の範囲では、単純な入れ子の代表格はリストである。 |
| **主張** | 丸括弧の連なりは気まぐれな発明というより、その条件を削ぎ落とした先に現れやすい形——発見——に見える（原記事の見方）。 |

#### J.1 思考実験：命令を「安全なデータ」にする

画面に線を引くプログラムがある、とします。手元なら `draw-line` を呼べばよい。困りごとを一つ足します。**遠くから送られてきた描画の指示を、こちらで実行したい。**

最初の思いつきは、「文面を、そのままプログラムとして走らせる」ことです。これは強すぎます。相手が書いた文字が、描画以外のことまでできてしまう。だから **許可した命令だけ** を、データの形で受け取ります。

命令カードのイメージです。

```text
名前: draw-line
材料: 点A, 点B, "blue"
```

キー名は毎回同じなので、省略できます。**先頭がすること、残りが材料**、という規則にします。思考実験では、命令の書き方を見やすくするために角括弧を使います。これは値としての `(list …)` や、本編 `cond` の枝とは別の「カードの書き方」です。Racket 本体では `[…]` と `(…)` は同じ意味なので、あとで丸括弧に揃えても中身の規則は変わりません。

```text
["draw-line", 点A, 点B, "blue"]
```

次に、材料の中にも命令を入れたくなります。

```text
["rotate", ["draw-line", 点A, 点B, "blue"], 90]
```

規則は二行で足ります。

1. リストでなければ、それはすでに値（点や色や数）である。  
2. リストなら、**先頭の名前は機械（関数）として探し**、残りの材料だけを先に値にして渡す。

先頭も材料と同じく「値にする」わけではありません。名前表から関数を引く、という一手が入ります。付録Iの I.3（手続きオブジェクト）で出てくる「機械」と同じ向きです。

序章 0.4 の「内側から外側へ値に落とす」も、材料側の話です。ここで出てくる再帰は、第2章のリスト処理と **形は似る** が、目的は「式を値にする」ことです。

さらに三つだけ足すと、命令の集まりは言語に近づきます。

- `do` … 複数の命令を順に行う  
- `def` … 名前を値（または関数）に結びつける  
- `fn` … 「今は計算せず、あとで使う機械」を作る  

`def` と `fn` は、本編の `define` と、付録Iの手続きオブジェクトに対応します。`do` は本線 BSL には出てきません。ここでは「まとめ役」だとだけ覚えてください。

安全な命令フォーマットを作ろうとしただけなのに、気づけば小さなプログラミング言語を書いています。

#### J.2 コードがデータであること

この配列言語には、ふつうの言語にはない手触りがあります。

ふだんの JavaScript では、変数を置く書き方（`const`）は言語が決めた構文です。利用者が `c` に改名することはできません。**ゲスト**として、作者の作法に従うイメージです。配列言語では `def` も `draw-line` も同じリストなので、組み込みと自分で足したものの差が、構文の壁としては薄い。原記事はこれを **共同経営者** に近い、と書いています。

コードがただのリストなら、コードを書き換えるコードも短くなります。たとえば「`unless` を、条件を否定した `if` に直す」作業です。

```text
["unless", 条件, 本体]
    ↓ 組み替え
["if", ["not", 条件], 本体]
```

ふつうの言語では、まず文を木に分解する道具（パーサ）が要ります。こちらでは、リストの先頭と中身を組み替えるだけで済む——いわゆるマクロです。本編では扱いません。

構造で編集できる、という利点もあります。文字ではなく「この枝」を広げたり、一段上げたりできる（Paredit など。発展）。カーソルが `条件` の前にあるとき、「否定の箱を被せる／剥がす」操作が、文字の切り貼りではなく枝の操作になります。

要するに、**プログラムそのものが、いつものデータ操作の対象**になります。

#### J.3 種明かし：それは Lisp の見た目である

角括弧を丸括弧に変え、カンマを消し、**名前として引くもの**を記号（引用符のない名前）にすると、本書の式と同じ家族に見えます。

区別だけ先に置きます。値として残す文字列（`"blue"`）は引用符付きのままです。名前として表を引くもの（`left` など）は、引用符を外した記号にします。点の値（`点L`）は、すでに値なので、どちらにもしません。

```text
["do",
  ["def", "draw-triangle",
    ["fn", ["left", "top", "right", "color"],
      ["do",
        ["draw-line", "left", "top", "color"],
        ["draw-line", "top", "right", "color"],
        ["draw-line", "left", "right", "color"]]]],
  ["draw-triangle", 点L, 点T, 点R, "blue"]]
```

```racket
; 見た目を整えたもの（イメージ。本編 BSL の練習問題ではない）
(define (draw-triangle left top right color)
  (draw-line left top color)
  (draw-line top right color)
  (draw-line left right color))
```

関数の本体では、並べた式を上から順に走らせるので、思考実験の `do` を書かなくてよい、という対応です。`define` が `def` と `fn` をまとめて引き受けます。

原記事は Clojure で同じ対応を示しています。規則は共通です。`(draw-line left top color)` は、「`left` `top` `color` を値にしてから、名前表で見つけた `draw-line` を走らせる」という意味です。

#### J.4 結論：削ぎ落とすとリストに着く

「プログラムをデータとして扱いたい。そのための、いちばん単純な入れ子は何か。」

XML でも JSON でも書けます。無駄を削ると、残るのは入れ子のリストに見えやすい、と原記事は誘導します。Lisp のカッコは、その答えの見た目に見えます。気まぐれに増えた飾りというより、条件を最適化した先に現れやすい形——だから **発明というより発見**——だ、と述べます。より良い表面文法があり得るかも、とも残しています。本書の式がこの形と同じ家族であることは、読み進めるうえでの嬉しい一致です（BSL を選んだ理由そのものではない）。
